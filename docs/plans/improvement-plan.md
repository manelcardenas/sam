## Phase 1 — SQL Database Migration (DynamoDB → Aurora PostgreSQL) + User Profiles ✅ DONE

> Historical: the Aurora target described here was later replaced by Neon (2026-05-30). The DynamoDB→SQL move, the `User` entity and the clean-architecture wiring all still stand — only the DB host changed.

**Goal:** Replace DynamoDB with PostgreSQL locally (Docker) and Aurora Serverless v2 in AWS. Add a real `User` entity.

### Architecture decision: Lambda + Aurora (public, no VPC)

> **This is the most important tradeoff in the entire plan.**

Lambda functions and relational databases do not pair naturally:
- Each Lambda invocation can open a new DB connection. At scale, you exhaust Aurora's connection limit.
- Aurora Serverless v2 with `minCapacity=0` has a **~30–60 second cold start** the first time it wakes up after being idle.
- At <100 users and low traffic this is acceptable, but the first request after a quiet period will be slow.

**Mitigations:**
1. Use `NullPool` on the SQLAlchemy engine — each request opens a fresh connection and closes it immediately, preventing connection leaks across Lambda invocations.
2. Do **not** use RDS Proxy (costs ~$20/month — too expensive for this use case).
3. Accept the cold start. Documented in the README.

**Key design choice — sync psycopg2, not async:**
Lambda runs one invocation per container. There are no concurrent requests sharing an event loop, so `async`/`await` provides zero benefit. Using sync `psycopg2` with `NullPool` is simpler, correct, and avoids the need to make the entire domain/use-case/port stack async. See `docs/knowledge/sync-vs-async.md` for the full rationale.

**Key design choice — public Aurora, Lambda outside VPC:**
Aurora is placed in public subnets with `publiclyAccessible=true`. Lambda runs outside the VPC and connects over the internet via password-secured TCP 5432. This eliminates the need for a NAT Gateway (~$35/month). See `docs/knowledge/vpc-vs-no-vpc.md` for the full rationale.

### What was implemented

#### 1. User entity & profile ✅

`domain/entities/user.py` promoted to a real entity:

```python
class User(BaseModel):
    id: str           # Cognito sub — not a UUID generated by us
    email: str
    display_name: str
    created_at: str
    updated_at: str
```

The `user_sub` from the Cognito JWT (`TokenPayload.sub`) is the primary key — we do not generate our own user IDs. On first authenticated request, a user record is created automatically (upsert). This ties every recipe and every restaurant review to a specific user.

## Phase 2 — Restaurant Reviews Service ✅ DONE (2026-07-11, PR #42)

> Shipped as designed: migration `874c491875f4_phase_2_restaurants_reviews`, the
> `Restaurant`/`Review`/`Cuisine` entities, their repositories and use cases, and the
> `restaurant_controller` routes. Authorization landed as specced (ADR-0002): restaurant
> facts editable by any authenticated user, reviews deletable only by their author, no
> restaurant-delete endpoint exposed.

**Goal:** Add a new domain — a shared, community-editable log of restaurants with per-user reviews, visible to every authenticated user of the app. See `CONTEXT.md` for the full domain glossary (Restaurant, Review, Category Score, Value, Price Level, Overall, Cuisine, Visited At).

> Superseded the original draft below (int 1–5 ratings, `food/service/ambiance/value/overall` categories, creator-only edits) after a design review with the user. Note this doc's Phase 1 section still targets Aurora; the project has since moved to Neon (see current `infra/` stack) — verify the actual DB target before writing the migration.

### Data model

```
Restaurant
  id           UUID PK
  created_by   str  FK → users.id (Cognito sub) — informational only, does not gate writes
  name         str
  address      str (optional)
  price_level  int (optional, 1–4, € to €€€€) — a fact about the venue, not a review score
  latitude     float (optional, nullable)  — reserved for Phase 2b (maps), unused for now
  longitude    float (optional, nullable)  — reserved for Phase 2b (maps), unused for now
  created_at   timestamptz
  updated_at   timestamptz

Cuisine
  id     UUID PK
  name   str (unique) — curated, extensible list (Italian, Japanese, Chinese, Indian,
                         Mediterranean, Spanish, Mexican, American, French, Thai,
                         Vegan/Vegetarian, Other). New entries are a data insert, no migration.

RestaurantCuisine (join table)
  restaurant_id  UUID FK → restaurants.id
  cuisine_id     UUID FK → cuisines.id

Review
  id             UUID PK
  restaurant_id  UUID FK → restaurants.id (CASCADE DELETE)
  user_id        str  FK → users.id (Cognito sub)
  location_score NUMERIC(3,1)  0.0–10.0, step 0.5  — location/decoration
  food_score     NUMERIC(3,1)  0.0–10.0, step 0.5
  service_score  NUMERIC(3,1)  0.0–10.0, step 0.5
  value_score    NUMERIC(3,1)  0.0–10.0, step 0.5  — value for money, NOT price_level
  comment        str (optional, max 1000 chars)
  visited_at     date  — defaults to today at creation; not editable afterwards (no review-edit in v1)
  created_at     timestamptz
  updated_at     timestamptz
```

**No unique constraint** on `(restaurant_id, user_id)` — a user can post multiple reviews of the same place over time. Revisits are the intended way to record a changed opinion, since reviews aren't editable in v1.

**`overall` is never stored** — always computed: per review, the average of the 4 category scores; per restaurant, the average of `overall` across all its reviews.

**Cascade delete:** deleting a restaurant would delete all its reviews — this is exactly why restaurant deletion is **not exposed in v1** (see Authorization rules).

### Location & map feature (deferred to Phase 2b)

v1 ships with **manual entry only** — no map, no autocomplete, no geocoding. `latitude`/`longitude` columns exist on `Restaurant` from day one but stay unused until Phase 2b, so adding map/Places search later needs no migration touching existing rows.

Phase 2b **shipped (scope A, 2026-07-11/12, PRs #42 + #43)**: **Geoapify** for Place search/autocomplete/nearby, superseding the earlier Google Places idea — Google's ToS forbids persisting Place facts (name/address/price) in our own DB, which is exactly SAM's data model. See `docs/adr/0003-geoapify-as-places-provider.md` for the decision and `docs/plans/geoapify-places-plan.md` for the implementation plan and what shipped. Area-anchored search was added on top of the original scope — see `docs/adr/0004-area-anchored-place-search.md`. Map *display* (scope B) is still open: no map library is installed yet, so `latitude`/`longitude` are stored but not yet rendered.

<details>
<summary>Original (superseded) map recommendation</summary>

For location, storing `latitude` / `longitude` as plain `FLOAT` columns is sufficient. The haversine formula (pure SQL math, no PostGIS) handles distance queries at this scale.

For the map view in the frontend, Leaflet.js + OpenStreetMap tiles are completely free, no API key, and work in a static Next.js export — Google Maps requires a billing account and API key management. This reasoning still applies to map *display*, but not to restaurant *search*, which the user wants Places-backed.

</details>

### Restaurant dedup (v1, no Places API yet)

Before creating a new restaurant, the create flow searches existing restaurants by name (case-insensitive `ILIKE`) and prompts the user to pick an existing match before falling back to "create new." A UX-level mitigation, not a hard constraint — duplicates can still occur.

### API routes

```
GET    /restaurants                          — search/list (?q=name for dedup search)
POST   /restaurants                          — create (auth required)
GET    /restaurants/{id}                     — detail with computed aggregate ratings
PUT    /restaurants/{id}                     — update facts (any authenticated user)
GET    /cuisines                             — list the curated cuisine vocabulary

GET    /restaurants/{id}/reviews             — list all reviews (scores + comment + visited_at + reviewer)
POST   /restaurants/{id}/reviews             — submit a review (auth required)
DELETE /restaurants/{id}/reviews/{review_id} — delete own review only
```

No `DELETE /restaurants/{id}` and no `PUT /restaurants/{id}/reviews/{review_id}` in v1.

### Authorization rules

- **Create restaurant:** any authenticated user
- **Update restaurant facts:** any authenticated user, no ownership check (ADR 0002)
- **Delete restaurant:** not exposed in v1
- **Submit review:** any authenticated user
- **Edit review:** not exposed in v1 — delete + re-create instead
- **Delete review:** only the review's `user_id`
- All endpoints require Cognito auth — no public/unauthenticated access

### Alembic migration

New migration `phase_2_restaurants_reviews.py`:
- Creates `restaurants` table (with nullable `latitude`/`longitude`)
- Creates `cuisines` table, seeded with the starter list
- Creates `restaurant_cuisines` join table
- Creates `reviews` table with FK to `restaurants` (`ON DELETE CASCADE`) and FK to `users`

### Reminder: CDK route registration

Every route above needs a matching `addRoutes()` entry in `infra/lib/application/lambda-api-stack.ts`, or API Gateway will 404 it even though the Lambda handles it fine.

## Phase 3 — GitHub Actions Pipelines ✅ DONE (2026-05-30) — shipped differently

**Goal:** move off two flat monolithic workflows (`test.yml`, `deploy.yml`) onto a
structure where a change to one part of the repo doesn't redeploy everything.

> **This phase was delivered, but not with the shape planned below.** The original
> design (a `ci.yml` + `deploy.yml` pair calling three `_reusable-*.yml` workflows,
> with migrations applied by invoking a dedicated migration Lambda) was dropped in
> favour of **three independent, path-filtered workflows**. The reusable-workflow
> indirection wasn't worth it for three jobs, and the migration Lambda was never
> built — CI runs Alembic directly, which is simpler and needs no extra deployed
> resource. The original plan is preserved at the bottom of this section for context.

### What actually exists

```
.github/workflows/
  pr-health-checks.yml   — quality gate: PRs + post-merge safety net on main
  deploy-backend.yml     — push to main touching backend/infra → migrate + deploy Lambda
  deploy-frontend.yml    — push to main touching frontend → deploy Amplify + start build
```

**`pr-health-checks.yml`** — three parallel jobs, no AWS credentials needed:
- `backend`: `uv sync --group dev`, `ruff check`, `ruff format --check`, `pytest tests/ -v`
- `frontend`: `npm ci`, `next lint`, `next build` (which is also the type-check gate; a
  placeholder `NEXT_PUBLIC_API_URL` is injected because the static export prerenders pages
  whose API-client constructor throws when it is unset)
- `infra`: `tsc --noEmit`, `npm test` (CDK jest assertions), `cdk synth --all`

**`deploy-backend.yml`** — OIDC into `AWS_ROLE_ARN`, then in one job:
1. **Migrations first** (expand-contract: additive schema before new code). The runtime
   DSN comes from SSM `/recipe-manager/db/dsn`, and the workflow strips `-pooler` from
   the host to derive Neon's **direct** endpoint — PgBouncer transaction pooling breaks
   Alembic's DDL and advisory locks.
2. `cdk deploy RecipeManagerLambdaApiStack --require-approval never`, then prints the API
   endpoint from `outputs.json`.

**`deploy-frontend.yml`** — OIDC, `cdk deploy RecipeManagerAmplifyStack` (fetching the
GitHub PAT from SSM and passing it via `--context`, since CloudFormation can't reference
a SecureString in `AWS::Amplify::App`), then `aws amplify start-job` to trigger the build.

### Design points worth keeping in mind

- **Path filters** on both deploy workflows mean a frontend-only PR never touches the
  Lambda, and vice versa.
- **`concurrency` groups**: deploys are serialised with `cancel-in-progress: false` (never
  kill a half-finished deploy); health checks use `cancel-in-progress: true` so only the
  newest commit on a branch is checked.
- **Deploys don't run tests** — `pr-health-checks.yml` also runs on push to `main` as the
  post-merge safety net.
- Both deploys are `workflow_dispatch`-able for manual runs.

### IAM `ci-role-stack.ts` — as shipped

DynamoDB permissions are gone. The role holds CloudFormation, Lambda create/update/delete
(scoped to `recipe-manager-*`), Amplify, ECR/asset-bucket access for CDK, and SSM
`GetParameter` + `kms:Decrypt` for the SecureStrings (Neon DSN, Geoapify key, GitHub PAT).
There is **no** `lambda:InvokeFunction` for a migration Lambda and **no** RDS/Secrets
Manager permissions — neither is needed: migrations run Alembic from the runner, and Neon
is not an AWS resource.
