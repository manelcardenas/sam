# Geoapify as the places provider; external identity stored on Restaurant

Phase 2b adds "select the restaurant you're at" — search/nearby lookup of real venues (Places) to create Mapped Restaurants from, prefilled with name, address, and coordinates. We chose **Geoapify** (OSM-backed) as the provider, proxied through the FastAPI backend so the API key stays server-side, and we store the picked Place's identity on the Restaurant as a nullable `external_place_id` with a partial unique index (creates with an already-known id return the existing Restaurant instead of a duplicate).

Google Places was the original plan (`docs/plans/improvement-plan.md` Phase 2b) and was rejected for a non-price reason: **Google's ToS forbids storing Places data beyond the place ID** (lat/lng max 30 days, name/address/price never) — persisting those facts in Postgres is exactly SAM's data model, so Google is legally incompatible regardless of quota, and it also requires a credit card. Geoapify is free at our scale (3,000 credits/day, no card) and **explicitly permits storing results permanently** with attribution ("Powered by Geoapify · © OpenStreetMap contributors" shown in the picker).

Consequences worth remembering: OSM data has no price level, ratings, or photos, so Price Level and Cuisine stay human-entered (cuisine tags are prefilled only when they match the curated vocabulary); `external_place_id` is Geoapify's format, so switching providers later means re-deriving identity (Geoapify also exposes the underlying OSM id, which would be the migration path); AWS Location Service was the runner-up (only provider that *sells* a storage license) but its free tier ends after 3 months, and Foursquare/Mapbox were rejected on free-tier size and storage ToS respectively.
